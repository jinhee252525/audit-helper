# 대용량(19만 건) 검색앱 아키텍처 비교

> 상황: 자체감사 지적 약 **190,471건(183MB)** + 기존 9,631건. 서버 없이 **정적 사이트(GitHub Pages)** 로 운영(인터넷망). 업무망 이전은 나중. 사용자는 공무원.
> 문제: 단일 `findings.json`을 브라우저가 한 번에 내려받아 검색하는 현재 방식은 183MB에선 불가능(로딩·메모리·속도 붕괴).

세 가지 방식을 원리 → 준비 → 동작 → 장단점 → 적합성 순으로 설명한다.

---

## 방식 A — 클라이언트 검색인덱스 + 샤딩 (추천)

**대표 도구:** FlexSearch, MiniSearch, Lunr (브라우저에서 도는 순수 JS 검색엔진)

### 원리
- 데이터를 미리 **작은 조각(shard)** 으로 나눠 저장하고(예: 연도별·기관유형별 JSON), 검색용 **색인(index)** 을 빌드 시점에 미리 만들어 둔다.
- 브라우저는 처음에 **색인만** 내려받아 메모리에 올리고, 검색어를 입력하면 색인에서 매칭되는 레코드 id를 즉시 찾는다.
- 실제 카드 상세는 매칭된 조각만 **필요할 때 지연 로드(lazy load)**.

### 데이터 준비(빌드 단계, 우리가 파이프라인으로)
1. 190k 레코드를 **필드 축소**한 검색용 경량 레코드로 변환(제목·지적요지·기관·연도·처분·id만).
2. FlexSearch 등으로 **역색인**을 만들어 `index/` 아래 분할 저장.
3. 상세 데이터는 `shards/2024.json`, `shards/공공기관.json` 처럼 분할 저장.

### 동작
- 최초 진입: 색인(수~수십 MB, 압축 시 더 작음) 로드 → 즉시 검색 가능.
- 검색: 밀리초 단위 매칭(오프라인 계산이라 빠름).
- 카드 열기: 해당 조각만 fetch.

### 장점
- **순수 정적** — GitHub Pages 그대로. 서버·DB 불필요.
- **오프라인 동작** 가능 → 나중에 **업무망(내부망) 이전에 최적**(인터넷 없이도 검색).
- 한국어 형태소는 아니지만 **n-gram/부분일치** 설정으로 국문 검색 실용적.
- 우리 F1(유사검색) 로드맵의 임베딩 시맨틱 검색과도 결합 쉬움.

### 단점
- 색인이 크면(19만 건) **초기 로드 용량**이 부담 → 샤딩·압축·필드 최소화로 관리 필요.
- 복합 필터(기관유형 AND 연도 AND 처분 AND 법령)를 색인만으로 다 처리하려면 설계가 정교해야 함.
- 정밀 랭킹·집계(대시보드 통계)는 별도 사전집계 필요.

### 이 프로젝트 적합성: ★★★★★
정적·오프라인·확장(임베딩) 3박자가 우리 요건(인터넷망 정적 → 업무망 이전)과 정확히 맞음.

## 방식 B — SQLite-wasm (브라우저 내 SQL)

**대표 도구:** sql.js / SQLite Wasm (+ 선택적으로 범위요청으로 부분로딩하는 sql.js-httpvfs)

### 원리
- 190k 레코드를 **하나의 `.sqlite` 파일**(정적 파일)로 만들어 배포.
- 브라우저가 WebAssembly로 SQLite 엔진을 띄우고 그 파일에 **SQL 쿼리**를 직접 실행.
- `sql.js-httpvfs`를 쓰면 파일 전체가 아니라 **필요한 페이지(블록)만 HTTP Range로 조금씩** 읽어 대용량도 가볍게 다룸.

### 데이터 준비
1. 파이프라인에서 `findings` 테이블 스키마로 **SQLite DB 생성**(인덱스 컬럼: 기관유형·연도·처분·work_type·법령).
2. FTS5(전문검색 확장)로 **지적내용 전문검색 인덱스** 추가.
3. `.sqlite` + (httpvfs 사용 시) 설정 JSON 배포.

### 동작
- 검색·필터·집계를 전부 **SQL 한 줄**로: `WHERE org_type='기초' AND year=2025 AND disposition='징계'` + `MATCH '계약'`.
- httpvfs면 초기 다운로드 거의 없이 쿼리마다 필요한 블록만 읽음.

### 장점
- **복합 필터·정렬·집계에 압도적으로 강함**(대시보드 KPI/통계와 궁합 최고).
- 183MB JSON이 SQLite로는 훨씬 **작아지고**(중복 텍스트 제거·바이너리), Range 로딩으로 **초기 부담 최소**.
- SQL이라 파이프라인·검증·중복제거(dedup) 쿼리도 동일 DB로 처리.

### 단점
- **구현 난도 상**: wasm 로딩, httpvfs 서버 설정(Range 지원 필요 — GitHub Pages는 Range 지원하므로 가능), 빌드 파이프라인 추가.
- 한국어 FTS 토크나이저 한계(부분일치 위해 trigram 토크나이저 설정 필요).
- 순수 정적이지만 초기 wasm(수백 KB~) 로딩과 브라우저 호환성 점검 필요.

### 이 프로젝트 적합성: ★★★★☆
데이터 규모·복합필터·대시보드에는 가장 강력. 다만 초기 구축 복잡도가 A보다 높음. 업무망 이전 시에도 정적 파일이라 유리.

## 방식 C — 범위 축소(핵심만 검색앱, 나머지 아카이브)

### 원리
- 담당자 실무 연관이 높은 부분만 `findings.json`(또는 A/B의 소규모 버전)에 싣고, **교육 개별학교 종합감사(약 66,000건)** 등 방대·저연관 데이터는 **검색 대상에서 빼고 아카이브**로만 보관.

### 예시 분할
- **싣기**: 중앙(4,911) + 지자체 광역·기초(약 2만) + 공공기관 지적 핵심 → 수만 건 규모(A 방식으로 충분히 가벼움).
- **아카이브**: 교육 개별학교(66k), 모범사례·경미 항목 → 별도 폴더/다운로드.

### 장점
- **가장 단순**·빠른 출시. 현재 정적 구조를 크게 안 바꿔도 됨.
- 담당자에게 **노이즈 적은** 결과(학교 종합감사가 검색을 뒤덮지 않음).

### 단점
- **완전성 훼손** — "다 수집" 취지와 배치됨. 교육/기타가 검색에서 빠짐.
- 나중에 범위를 넓히려면 결국 A/B가 필요.

### 이 프로젝트 적합성: ★★★☆☆
빠른 MVP엔 좋으나, 이미 전량 수집했으므로 "검색에서 빼는" 선택은 아까움. A/B의 **필터 기본값**으로 대체 가능(교육은 기본 숨김, 원하면 켜기).

## 종합 권고

| 기준 | A 인덱스+샤딩 | B SQLite-wasm | C 범위축소 |
|---|---|---|---|
| 정적(GitHub Pages) | ✅ | ✅(Range) | ✅ |
| 대용량 19만 | ○(샤딩) | ◎ | △(뺌) |
| 복합필터·대시보드 | △(사전집계) | ◎ | ○ |
| 오프라인·업무망 이전 | ◎ | ○ | ◎ |
| 구축 난도 | 중 | 상 | 하 |
| 확장(임베딩 F1) | ◎ | ○ | ○ |

**추천 조합:**
1. **1차: 방식 A(FlexSearch + 연도·기관유형 샤딩)** 로 전량 검색 구현 + **교육 개별학교는 필터 기본 숨김**(방식 C의 장점 흡수).
2. **대시보드 통계는 사전집계 JSON**(빌드 시 계산) 로 별도 제공(방식 A의 약점 보완).
3. 복합쿼리·규모가 더 커지면 **방식 B(SQLite-wasm)** 로 승격.

즉 **A를 기본 골격**으로 하고 C(필터 기본값)·B(향후 승격)를 보완재로 쓰는 것이 이 프로젝트에 가장 합리적이다.
